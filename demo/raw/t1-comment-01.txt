## CRITICAL — `RewardDistributor.claim()` never zeros `accrued[msg.sender]`

**File:** `src/rewards/RewardDistributor.sol`
**Function:** `claim()` (lines 125–135)

**What an attacker can do:** Drain the entire reward-token balance of `RewardDistributor` by calling `claim()` in a loop, extracting the same accrued balance repeatedly without any additional staking or waiting.

**Root cause:** `accrued[msg.sender]` is read and paid out, but never reset to zero. `userIndex[msg.sender]` is correctly updated to `globalIndex`, which zeroes out `_pendingFor`, but the value that was previously folded into `accrued` by `checkpoint` is never cleared.

```solidity
function claim() external nonReentrant returns (uint256 amount) {
    amount = accrued[msg.sender] + _pendingFor(msg.sender);
    if (amount == 0) revert NothingToClaim();

    userIndex[msg.sender] = globalIndex;   // _pendingFor → 0 after this
    totalClaimed += amount;

    rewardToken.safeTransfer(msg.sender, amount);
    // ❌ accrued[msg.sender] is never set to 0
    emit Claimed(msg.sender, amount);
}
```

**Conditions required:**
1. The attacker must have a positive `accrued[account]` balance. This is set by `checkpoint()`, which the vault calls in `deposit()` and `requestWithdrawal()` for the caller — so any user who stakes, earns rewards during a subsequent reward notification, and then triggers a second deposit or withdrawal request will accumulate a non-zero `accrued` value.
2. After that, calling `claim()` repeatedly is sufficient. Each call transfers the same `accrued` amount. No reentrancy, special token, or privileged access is needed.

**Concrete attack path:**
1. Attacker stakes 100 tokens (first deposit; `accrued = 0`).
2. Owner calls `notifyReward(50 ether)`.
3. Attacker makes a second small deposit, causing the vault to call `checkpoint(attacker)`. This writes `accrued[attacker] = 50 ether` and advances `userIndex[attacker] = globalIndex`.
4. Attacker calls `claim()` → receives 50 ether; `accrued[attacker]` remains 50 ether.
5. Attacker calls `claim()` again → receives another 50 ether.
6. Repeat until the reward pool is empty.

**Fix:** Add `accrued[msg.sender] = 0;` before the `safeTransfer` call in `claim()`.

The test at `RewardDistributor.t.sol:102–117` covers the checkpoint-then-claim path but does not assert that a second `claim()` reverts, leaving the bug undetected.

## MEDIUM — `deposit()` updates state before receiving tokens (CEI violation)

**File:** `src/core/StakingVault.sol`
**Function:** `deposit()` (lines 124–139)

**What an attacker can do:** With a callback-capable staking asset (ERC-777, or any ERC-20 with transfer hooks such as a fee-on-transfer token that invokes a hook), the token's `transferFrom` callback fires after shares have been minted and `totalAssets`/`totalSupply`/`balanceOf` have already been updated. During that window the vault's internal accounting reflects a deposit that has not yet been funded.

```solidity
totalAssets += assets;          // ← state updated
totalSupply += shares;
balanceOf[msg.sender] += shares;

asset.safeTransferFrom(msg.sender, address(this), assets);  // ← tokens arrive here
```

**Conditions required:**
- The staking asset must invoke a callback on the sender or receiver during `transferFrom`.
- `StakingVault`'s own `nonReentrant` guard (shared `_entered` flag) blocks a re-entry back into `deposit`, `requestWithdrawal`, `completeWithdrawal`, or `accrueYield`. However, `RewardDistributor` has an independent `_entered` flag. A callback could call `RewardDistributor.claim()` or `notifyReward()` (if the caller is the owner) while the vault's accounting is transiently inconsistent.

**Impact:** With the current `RewardDistributor`, a callback into `claim()` during this window would allow a user whose `accrued` balance was built up across multiple `checkpoint` calls to claim those rewards using the already-updated (inflated) share balance for any future `_pendingFor` computation. In the present code the impact is bounded because `checkpoint` resets `userIndex = globalIndex` at the top of `deposit`, making `_pendingFor` return 0 for the current depositor during the callback. The impact escalates if the token or `RewardDistributor` logic changes.

**Fix:** Move the `safeTransferFrom` call to before the state updates, following the Checks-Effects-Interactions pattern.

## LOW — `transferOwnership` accepts `address(0)`, silently blocking ownership transfer

**File:** `src/auth/Ownable2Step.sol`
**Function:** `transferOwnership()` (lines 30–33)

**What an attacker can do:** A compromised or inattentive owner can call `transferOwnership(address(0))`, setting `pendingOwner` to the zero address. Since no one controls `address(0)`, `acceptOwnership()` can never be called, making the pending transfer permanently stuck. The existing owner retains control, but the intent to transfer ownership is silently broken — this is especially dangerous if the call was meant to renounce ownership.

**Conditions required:** Owner calls `transferOwnership(address(0))`, whether by mistake or coercion.

**Fix:** Add `require(newOwner != address(0), "OWNER_ZERO");` in `transferOwnership`, mirroring the check in the constructor.

## LOW — `setGuardian` accepts `address(0)` without validation

**File:** `src/core/StakingVault.sol`
**Function:** `setGuardian()` (lines 201–204)

**What an attacker can do:** The owner can set `guardian = address(0)`. Once set, the `pause()` function (`msg.sender != owner && msg.sender != guardian`) still permits the owner to pause, but the secondary fast-pause capability (intended for incident response) is silently lost. There is also no check in the constructor for `initialGuardian`, so the vault can be deployed without a functioning guardian with no warning.

**Conditions required:** Owner calls `setGuardian(address(0))`, or the vault is deployed with `initialGuardian = address(0)`.

**Fix:** Add a zero-address check in `setGuardian` (and optionally in the constructor if a guardian is considered required).

## Informational — `nonReentrant` initialises guard to `0`, paying cold SSTORE cost on every entry

**File:** `src/core/StakingVault.sol`, `src/rewards/RewardDistributor.sol`

Both contracts declare `uint256 private _entered;` (default value `0`) and toggle `0 → 1 → 0` on every guarded call. The first write to a zero slot costs ~20,000 gas (cold SSTORE), paid again after each call resets the slot to `0`. The conventional approach initialises the slot to `1` at construction and toggles to `2`/back, keeping the slot warm (2,900 / 100 gas). No security impact; only a gas efficiency concern.
