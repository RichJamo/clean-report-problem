## CRITICAL

### C-1: `RewardDistributor.claim()` never resets `accrued[msg.sender]` — complete reward pool drainage

**File:** `src/rewards/RewardDistributor.sol:125–135`

**What an attacker can do:**
Call `claim()` in back-to-back transactions to withdraw the same `accrued` balance an unlimited number of times, draining the entire reward token balance of the contract.

**Conditions required:**
The attacker must have a non-zero `accrued[attacker]` balance. This is accumulated by the vault calling `checkpoint` before any balance change (deposit or withdrawal request). Once any checkpoint has ever been recorded for the account, the drain is possible.

**Root cause:**
`claim()` sets `userIndex[msg.sender] = globalIndex` (so `_pendingFor` returns 0 on repeat calls) but never clears `accrued[msg.sender]`. On each repeat call:

```
amount = accrued[msg.sender] + _pendingFor(msg.sender)
       = accrued[msg.sender] + 0          // userIndex == globalIndex after first claim
       = accrued[msg.sender]              // unchanged — still the original value
```

Because `amount != 0`, the `NothingToClaim` guard does not fire, tokens are transferred again, and `accrued[msg.sender]` remains at its original value for the next call. The loop repeats until the contract holds no reward tokens.

The fix is one line: `accrued[msg.sender] = 0;` before the transfer.

## MEDIUM

### M-1: `deposit()` is incompatible with fee-on-transfer tokens — `totalAssets` overstatement

**File:** `src/core/StakingVault.sol:124–139`, specifically `deposit()`

**What an attacker can do:**
If the vault is deployed with a fee-on-transfer ERC-20 as the asset, every deposit records `totalAssets += assets` while the vault actually receives `assets - fee`. Over time `totalAssets` grows faster than the vault's real balance. New depositors receive fewer shares than they are entitled to (share price is artificially inflated), and eventually some withdrawal requests cannot be settled because the vault is short of tokens.

**Conditions required:**
The staked asset is a fee-on-transfer token. The contract performs no balance-snapshot check (`balanceOf(address(this))` before and after the transfer). The same issue exists in `accrueYield()` (line 188).

---

### M-2: `completeWithdrawal()` uses the live fee recipient, not the one at request time

**File:** `src/core/StakingVault.sol:166–178`, function `completeWithdrawal()`

**What an attacker can do:**
The fee rate is correctly locked at request time (stored in `WithdrawalQueue`), but `feeController.feeRecipient()` is fetched live at completion time. If the owner (or a compromised owner key) calls `FeeController.setFeeRecipient()` between a user's `requestWithdrawal` and `completeWithdrawal`, the exit fee is redirected to the new address. Combined with `setWithdrawalFeeBps` raising the fee to the 5% cap just before new requests are enqueued, a malicious or compromised owner can silently capture 5% of all new exits.

**Conditions required:**
Owner key compromise or a malicious owner. Users already in the cooldown period are protected (their fee rate is locked), but new withdrawal requests are not.

---

### M-3: `accrueYield()` and `notifyReward()` can be sandwiched by a frontrunner

**File:** `src/core/StakingVault.sol:183`, `src/rewards/RewardDistributor.sol:109`

**What an attacker can do:**
An attacker who observes a pending `accrueYield` or `notifyReward` transaction can deposit just before it executes, receiving shares at the pre-yield price. Their shares immediately appreciate, and for reward notifications their new balance earns the full per-share reward. The cooldown on withdrawals partially mitigates this for `accrueYield` (the attacker must wait N days), but `notifyReward` rewards can be claimed immediately after a `checkpoint`.

**Conditions required:**
Attacker can observe the mempool (standard on public networks). No slippage guard or snapshot mechanism prevents this.

## LOW

### L-1: `deposit()` has no minimum-shares output guard

**File:** `src/core/StakingVault.sol:124`, function `deposit()`

**What an attacker can do:**
There is no `minShares` parameter. If the exchange rate changes between a user signing a transaction and it being included (e.g., due to `accrueYield` being mined first), the user receives fewer shares than expected with no on-chain protection. This enables MEV extraction without any recourse for the victim.

**Conditions required:**
Any block-level reordering or front-run of the user's `deposit` transaction.

---

### L-2: `WithdrawalCompleted` event emits net payout, not gross assets, in the `assets` field

**File:** `src/core/StakingVault.sol:71, 177`

```solidity
event WithdrawalCompleted(address indexed account, uint256 indexed id, uint256 assets, uint256 fee);
// ...
emit WithdrawalCompleted(msg.sender, id, paid, fee);   // `paid` = assets - fee
```

**What an attacker can do:**
No direct exploit, but any off-chain indexer, analytics tool, or bridge that reads the `assets` field from this event will receive the post-fee amount while believing it is the gross amount. This can cause double-counting or accounting discrepancies in downstream systems.

**Conditions required:**
Any consumer of the event that interprets `assets` as the gross redeemed amount.

---

### L-3: `setGuardian()` accepts the zero address without validation

**File:** `src/core/StakingVault.sol:201`, function `setGuardian()`

**What an attacker can do:**
Setting `guardian = address(0)` silently removes the emergency pause capability without any notice or event indicating intent. The `pause()` function check `msg.sender != owner && msg.sender != guardian` would still pass for the owner, but the secondary circuit breaker is eliminated.

**Conditions required:**
Owner calls `setGuardian(address(0))`, either accidentally or under duress.

## INFORMATIONAL

### I-1: `Ownable2Step.transferOwnership()` accepts `address(0)` as `newOwner`

**File:** `src/auth/Ownable2Step.sol:30`, function `transferOwnership()`

Setting `pendingOwner = address(0)` is effectively safe because `acceptOwnership` requires `msg.sender == pendingOwner` and `address(0)` cannot send transactions. It can be used to cancel a pending transfer, which may be intentional. However, the lack of an explicit `address(0)` guard can confuse off-chain monitoring (the `OwnershipTransferStarted` event fires with `newOwner = address(0)`).
