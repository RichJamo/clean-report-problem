## Finding 1 — CRITICAL: Reward token fully drainable via repeated `claim()`

**File:** `src/rewards/RewardDistributor.sol`
**Function:** `claim()` (line 125)

### What an attacker can do

Call `claim()` repeatedly across separate transactions to drain the entire reward token balance of the contract, well beyond their legitimate entitlement.

### Root cause

`claim()` reads `accrued[msg.sender]` and pays it out but **never resets it to zero**:

```solidity
function claim() external nonReentrant returns (uint256 amount) {
    amount = accrued[msg.sender] + _pendingFor(msg.sender);
    if (amount == 0) revert NothingToClaim();

    userIndex[msg.sender] = globalIndex;   // ← index is updated
    totalClaimed += amount;

    rewardToken.safeTransfer(msg.sender, amount);  // ← tokens leave
    // ← accrued[msg.sender] is NEVER zeroed
}
```

`accrued[msg.sender]` is populated by `checkpoint()` (called by the vault before every share balance change). After `claim()` returns, the storage slot still holds the original checkpointed amount. On the next call `_pendingFor` returns 0 (the index was advanced), but `accrued[msg.sender]` is still non-zero, so `amount` is the same as the first call. The transfer succeeds as long as the contract holds reward tokens.

### Step-by-step exploit

1. Alice stakes 100 asset tokens and receives 100 shares.
2. Owner calls `notifyReward(100)` → `globalIndex = 1e18`.
3. Alice deposits 1 more asset token. The vault calls `checkpoint(alice)`:
   - `pending = 100 × (1e18 − 0) / 1e18 = 100`
   - `accrued[alice] = 100`, `userIndex[alice] = 1e18`
4. Alice calls `claim()`:
   - `amount = 100 + 0 = 100`. Transfers 100 reward tokens. `accrued[alice]` unchanged.
5. Alice calls `claim()` again:
   - `amount = 100 + 0 = 100`. Transfers 100 more reward tokens.
6. Repeat until the contract's reward token balance is exhausted.

### Conditions required

- The attacker must hold vault shares when at least one `notifyReward` has been called (so `globalIndex > 0`).
- The vault must have called `checkpoint(attacker)` at some point after that notification (triggered by any deposit or withdrawal request), which writes a non-zero value into `accrued[attacker]`.
- Any legitimate staker who has ever deposited or withdrawn satisfies both conditions automatically.

### Fix

Add `accrued[msg.sender] = 0;` immediately before or after the transfer in `claim()`.

## Finding 3 — MEDIUM: Unchecked intermediate multiplication in `mulDiv` enables arithmetic DoS

**File:** `src/libraries/FixedPointMath.sol`
**Function:** `mulDiv()` (line 14), used at `StakingVault.sol:110,117,169` and `RewardDistributor.sol:118,143`

### What an attacker can do

Cause `deposit()`, `convertToShares()`, `convertToAssets()`, `completeWithdrawal()`, and `notifyReward()` to revert unconditionally for any call that overflows the intermediate product, effectively freezing vault operations for affected users or amounts.

### Root cause

```solidity
function mulDiv(uint256 x, uint256 y, uint256 d) internal pure returns (uint256) {
    return (x * y) / d;   // ← x * y checked, reverts on overflow
}
```

Solidity 0.8's checked arithmetic makes an overflow revert instead of wrap, so no funds are at risk — but any code path reaching `mulDiv` with `x × y > type(uint256).max` is permanently broken for that input.

Affected call sites:

| Call site | Expression | Overflow condition |
|---|---|---|
| `convertToShares` | `assets × totalSupply` | both large |
| `convertToAssets` | `shares × totalAssets` | both large |
| `completeWithdrawal` | `assets × feeBps` | `assets > 2^256 / 500` |
| `notifyReward` | `amount × WAD` | `amount > 2^256 / 1e18` |
| `_pendingFor` | `balance × delta` | both large |

For tokens with 18 decimals the practical overflow threshold in the fee calculation is `assets > ~2.3 × 10^75`, which is out of reach for realistic tokens. However, tokens with very high supply or small decimals can reach the threshold in `convertToShares`/`convertToAssets`.

### Fix

Replace the naïve `(x * y) / d` with a 512-bit intermediate (e.g., Solady `FullMath.mulDiv` or OpenZeppelin's equivalent) so the result is always computable without overflow.

## Finding 4 — LOW: `setGuardian` silently accepts `address(0)`, disabling the guardian role without ceremony

**File:** `src/core/StakingVault.sol`
**Function:** `setGuardian()` (line 201)

### What an attacker can do

This is an owner-only function, so exploitation requires a compromised or careless owner. If `guardian` is set to `address(0)`, the guardian role is vacated without any log entry distinguishing intent from mistake.

```solidity
function setGuardian(address newGuardian) external onlyOwner {
    emit GuardianUpdated(guardian, newGuardian);
    guardian = newGuardian;   // no zero-address check
}
```

The constructor also accepts `address(0)` for `initialGuardian`. A zero guardian simply means only the owner can call `pause()`, which may be intentional but is not documented.

### Conditions required

Owner calls `setGuardian(address(0))` deliberately or by mistake (e.g., mistyped calldata).

### Fix

Add `require(newGuardian != address(0), "GUARDIAN_ZERO")` if a guardian is always expected, or add a NatSpec note that `address(0)` is a valid sentinel meaning "no guardian" if the current behaviour is intentional.

## Finding 5 — LOW: `WithdrawalQueue` cooldown period unchecked at construction

**File:** `src/core/WithdrawalQueue.sol`
**Location:** Constructor (line 50), via `StakingVault` constructor (line 101)

### What an attacker can do

This is a deployer-time misconfiguration risk rather than an in-protocol exploit. Setting `cooldown_ = 0` removes the exit delay entirely, defeating its purpose. Setting `cooldown_ = type(uint64).max` (approximately 585 billion years) makes every withdrawal request permanently unclaimable, permanently locking all staked funds.

```solidity
constructor(address vault_, uint64 cooldown_) {
    require(vault_ != address(0), "VAULT_ZERO");
    vault = vault_;
    cooldown = cooldown_;   // no range check
}
```

Because `cooldown` is immutable, there is no on-chain recovery path once the contract is deployed with a bad value.

### Conditions required

Misconfiguration at deployment time. The `WithdrawalQueue` is created inside the `StakingVault` constructor, so the deployer must pass a sane `cooldown_` to `StakingVault`.

### Fix

Add bounds checks in the constructor, e.g.:

```solidity
require(cooldown_ >= MIN_COOLDOWN && cooldown_ <= MAX_COOLDOWN, "COOLDOWN_OUT_OF_RANGE");
```

and define `MIN_COOLDOWN` / `MAX_COOLDOWN` as named constants so the acceptable range is documented and testable.

## Notes on items reviewed and found sound

- **Reentrancy guards**: both `StakingVault` and `RewardDistributor` use a storage-based `_entered` flag with the correct initial value (0) and correctly bracket the full function body, including all external calls.
- **Withdrawal queue double-settle**: the `settled` boolean is set before any transfer and is checked at the top of `settle()`; double-claiming is prevented.
- **Share-price manipulation via donations**: `totalAssets` is tracked in storage and updated only through controlled entry points; unsolicited token transfers cannot move the share price.
- **Fee-rate lock**: the fee rate is snapshotted into each `WithdrawalQueue.Request` at request time; a subsequent `setWithdrawalFeeBps` cannot retroactively change the terms of a pending exit.
- **Reward checkpoint ordering**: the vault calls `_checkpoint(account)` before every share balance mutation; rewards are always accumulated at the pre-change balance.
- **Two-step ownership**: `Ownable2Step` correctly requires the nominee to accept before ownership moves; a mistyped address cannot strand the contract.
- **`totalClaimed` accounting**: `totalClaimed` in `RewardDistributor` is incremented unconditionally on each `claim()` call. Because the `accrued` bug (Finding 1) allows more claims than tokens were notified, `totalClaimed` will exceed `totalNotified` in an exploited contract. This is a symptom of Finding 1, not an independent vulnerability.
