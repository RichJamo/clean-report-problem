## C-1 — Critical: `claim()` never clears `accrued[msg.sender]`

**File:** `src/rewards/RewardDistributor.sol`  
**Function:** `claim()` (line 125)

### What an attacker can do

After earning any amount of rewards an attacker may call `claim()` in a loop across multiple transactions to drain the entire `rewardToken` balance of the contract. Each iteration pays out the same previously-earned amount again because it is never erased.

### Conditions required

1. The attacker must have previously had a non-zero `accrued[attacker]` balance (i.e. they must have staked and had a `checkpoint` called, or they must have staked when `globalIndex > 0`). Even a dust amount suffices.
2. `notifyReward` need not be called again between iterations — the stale `accrued` value is re-read each time.

### Root cause

```solidity
// RewardDistributor.sol:125-135
function claim() external nonReentrant returns (uint256 amount) {
    amount = accrued[msg.sender] + _pendingFor(msg.sender);
    if (amount == 0) revert NothingToClaim();

    userIndex[msg.sender] = globalIndex;   // ✓ index reset
    totalClaimed += amount;

    rewardToken.safeTransfer(msg.sender, amount);  // tokens leave
    // ✗ accrued[msg.sender] is never set to 0
    emit Claimed(msg.sender, amount);
}
```

After the first successful call:

| State variable | Value |
|---|---|
| `userIndex[msg.sender]` | `globalIndex` (updated) |
| `accrued[msg.sender]` | unchanged — still holds the original accrued amount |

On the second call:

- `_pendingFor(msg.sender)` returns `0` because `globalIndex - userIndex[msg.sender] == 0`.
- `amount = accrued[msg.sender] + 0` — the same non-zero value as before.
- The `if (amount == 0)` guard does **not** revert.
- Another transfer goes out.

This repeats until the contract's `rewardToken` balance is exhausted.

### Fix

Add `accrued[msg.sender] = 0;` before (or immediately after) the transfer:

```solidity
accrued[msg.sender] = 0;
userIndex[msg.sender] = globalIndex;
totalClaimed += amount;
rewardToken.safeTransfer(msg.sender, amount);
```

## L-1 — Low: `transferOwnership` accepts `address(0)` as the nominee

**File:** `src/auth/Ownable2Step.sol`  
**Function:** `transferOwnership()` (line 30)

### What an attacker can do

An owner who accidentally (or under duress) calls `transferOwnership(address(0))` sets `pendingOwner = address(0)`. Because `address(0)` can never call `acceptOwnership()`, the pending transfer is permanently stuck. The current owner retains all privileges and can issue another `transferOwnership` to correct the mistake, so this does not result in lost access. The risk is confusion, unnecessary event emissions, and a temporarily misleading `pendingOwner` state visible on-chain.

### Conditions required

Owner calls `transferOwnership` with a zero address argument (e.g., a scripting error or UI bug).

### Root cause

```solidity
// Ownable2Step.sol:30-33
function transferOwnership(address newOwner) external onlyOwner {
    pendingOwner = newOwner;   // no address(0) guard
    emit OwnershipTransferStarted(owner, newOwner);
}
```

### Fix

```solidity
require(newOwner != address(0), "NOMINEE_ZERO");
```

## I-1 — Informational: `mulDiv` uses plain multiplication; reverts on extreme inputs

**File:** `src/libraries/FixedPointMath.sol`  
**Function:** `mulDiv()` (line 14)

```solidity
function mulDiv(uint256 x, uint256 y, uint256 d) internal pure returns (uint256) {
    return (x * y) / d;  // overflows if x * y > type(uint256).max
}
```

Solidity 0.8.x reverts on overflow, so no value is corrupted. However, large but legitimate inputs — such as a very large notified reward amount combined with a tiny share supply — could cause `notifyReward` to revert permanently, preventing reward distribution. The overflow threshold (~1.16 × 10⁵⁹ for the WAD-scaled path) is well beyond any realistic ERC-20 supply with 18 decimals, making this a theoretical DoS rather than a practical exploit.

### Fix

Replace with a 512-bit-product `mulDiv` (e.g., Uniswap v3's or OpenZeppelin's implementation) that avoids the intermediate overflow constraint.

## I-2 — Informational: Reentrancy guard uses 0→1→0 transitions (gas cost)

**Files:** `src/core/StakingVault.sol` (line 77), `src/rewards/RewardDistributor.sol` (line 64)

```solidity
modifier nonReentrant() {
    if (_entered == 1) revert Reentrancy();
    _entered = 1;   // 0 → nonzero: 20,000 gas (cold SSTORE)
    _;
    _entered = 0;   // nonzero → 0: refund path
}
```

The conventional 1→2→1 pattern (initialising the slot to `1` at deployment) avoids the expensive zero-to-nonzero write on every call, saving roughly 15,000 gas per guarded function invocation. There is no security impact — the guard is logically correct.

### Fix

Initialise `_entered = 1` in both contracts' constructors and change the guard to `if (_entered == 2) revert Reentrancy(); _entered = 2; ...; _entered = 1;`.

## Out-of-scope observations (no vulnerability, noted for completeness)

- **Inflation attack is correctly mitigated.** `totalAssets` is tracked in storage, not read from `token.balanceOf(address(this))`, so a direct token donation cannot inflate the share price.
- **Fee is correctly snapshotted at request time.** Each `WithdrawalQueue.Request` stores the `feeBps` in force when it was created; a later fee change cannot be applied retroactively.
- **Two-step ownership transfer is correctly implemented** in all contracts that use `Ownable2Step`, preventing ownership loss from a mistyped address (subject to L-1 above).
- **Share-dilution MEV.** A staker who front-runs `notifyReward` with a deposit earns a share of that reward distribution. The cooldown and withdrawal fee significantly reduce the profitability of such an attack, but cannot eliminate it entirely. This is an inherent property of snapshot-at-notify reward schemes.
