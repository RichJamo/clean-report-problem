## CRITICAL — 1 finding

### [C-1] `RewardDistributor.claim()` never zeros `accrued[msg.sender]` — unlimited reward drain

**File:** `src/rewards/RewardDistributor.sol`  
**Function:** `claim()` (line 125)

**What an attacker can do:** Call `claim()` in a loop (or in separate transactions) to withdraw the same accrued reward balance over and over, draining the entire `rewardToken` balance held by the distributor.

**Conditions required:** The attacker must have called `claim()` at least once successfully — i.e., they must have had a non-zero claimable balance at some point (which any legitimate staker will have after `notifyReward` is called).

**Root cause:** The function computes `amount = accrued[msg.sender] + _pendingFor(msg.sender)` and then sets `userIndex[msg.sender] = globalIndex` (zeroing future pending rewards), but it never executes `accrued[msg.sender] = 0`. On every subsequent call, `_pendingFor` returns 0 (because `userIndex == globalIndex`), but `accrued[msg.sender]` still holds its original value, so `amount` is the same and the transfer fires again.

```solidity
// src/rewards/RewardDistributor.sol:125-135
function claim() external nonReentrant returns (uint256 amount) {
    amount = accrued[msg.sender] + _pendingFor(msg.sender);
    if (amount == 0) revert NothingToClaim();

    userIndex[msg.sender] = globalIndex;
    totalClaimed += amount;

    rewardToken.safeTransfer(msg.sender, amount);   // transfers again every call
    // ← accrued[msg.sender] is never reset to 0
    emit Claimed(msg.sender, amount);
}
```

**Fix:** Add `accrued[msg.sender] = 0;` before the transfer.

## LOW — 2 findings

### [L-1] `setRewardDistributor` can permanently DoS deposits and withdrawal requests

**File:** `src/core/StakingVault.sol`  
**Function:** `setRewardDistributor()` (line 194)

**What an attacker can do:** If the owner is compromised, or the owner itself is malicious, setting `rewardDistributor` to a contract whose `checkpoint()` always reverts will permanently block every call to `deposit()` and `requestWithdrawal()`. Because `_checkpoint` is called without a `try/catch`, a reverting distributor propagates the revert to the caller.

**Conditions required:** The `rewardDistributor` slot must not yet be set (i.e., this is the first call to `setRewardDistributor`). Once set, it cannot be changed (`DistributorAlreadySet` prevents a second write). Stakers who already have pending withdrawal requests can still call `completeWithdrawal`, but no new withdrawal requests can be opened, trapping any staker who has not yet acted.

```solidity
// src/core/StakingVault.sol:222-227
function _checkpoint(address account) private {
    IRewardDistributor distributor = rewardDistributor;
    if (address(distributor) != address(0)) {
        distributor.checkpoint(account);   // no try/catch; a revert propagates
    }
}
```

**Fix:** Wrap `distributor.checkpoint(account)` in a `try/catch`, or allow the owner to replace the distributor.

### [L-2] Reentrancy guard uses uninitialized-zero storage slot (0/1 pattern)

**Files:** `src/core/StakingVault.sol` (line 59), `src/rewards/RewardDistributor.sol` (line 52)  
**Function:** `nonReentrant` modifier in both contracts

**What an attacker can do:** This is a gas-efficiency issue, not an exploitable security vulnerability. The guard is logically correct. However, because `_entered` starts at 0 (uninitialized), the first call into any `nonReentrant` function pays a cold-slot SSTORE (22,100 gas, 0→1) and then a partial refund on exit (1→0). The standard 1/2 pattern (slot initialized to 1 in the constructor) pays only a warm-slot SSTORE (100 gas) on every call after construction.

**Conditions required:** Any user interacting with these functions pays elevated gas costs on the first call per slot-warm cycle.

## INFORMATIONAL — 1 note

### [I-1] `FixedPointMath.mulDiv` uses unchecked intermediate multiplication

**File:** `src/libraries/FixedPointMath.sol`, line 14

`(x * y) / d` will revert (via Solidity 0.8.x overflow checking) if `x * y > type(uint256).max`. In `RewardDistributor.notifyReward`, the expression `amount.mulDiv(WAD, supply)` overflows when `amount > type(uint256).max / 1e18` (~1.16 × 10⁵⁹ tokens). This is beyond any realistic token supply, so there is no practical exploitability. Using a full 512-bit intermediate (as in OpenZeppelin's `Math.mulDiv`) would eliminate the theoretical revert path and is a best-practice recommendation.
