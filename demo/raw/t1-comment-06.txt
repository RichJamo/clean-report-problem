## Critical

### C-1 — `RewardDistributor.claim()` never clears `accrued`, enabling unlimited drain

**File:** `src/rewards/RewardDistributor.sol`  
**Function:** `claim()` (line 125)

**What an attacker can do:** Any staker whose `accrued[account]` mapping has been written to a nonzero value can call `claim()` in a tight loop and drain every reward token held by the contract.

**The bug:** `claim()` reads `accrued[msg.sender]` into the return variable and transfers that amount, but it never writes `accrued[msg.sender] = 0`. On every subsequent call the same non-zero balance is re-read and re-paid.

```solidity
function claim() external nonReentrant returns (uint256 amount) {
    amount = accrued[msg.sender] + _pendingFor(msg.sender);
    if (amount == 0) revert NothingToClaim();

    userIndex[msg.sender] = globalIndex;   // clears pending
    totalClaimed += amount;

    rewardToken.safeTransfer(msg.sender, amount);  // pays out accrued …
    // … but accrued[msg.sender] is never zeroed
}
```

**Conditions required:**
1. `accrued[msg.sender]` must be nonzero. This is set by `checkpoint()`, which the vault calls unconditionally before every deposit and withdrawal request. So any staker who stakes, earns at least one round of rewards, and then deposits or requests a withdrawal again will have `accrued > 0`.
2. The contract must hold reward tokens (it must, for any rewards to have been notified).
3. The reentrancy guard prevents the exploit within a single transaction, but it is not needed: separate transactions each pass the `nonReentrant` check and each steal the same amount.

**Concrete exploit:**
1. Alice stakes 100 tokens.  
2. Owner calls `notifyReward(1000)`.  
3. Alice stakes 1 more token → vault calls `checkpoint(alice)` → `accrued[alice] = 1000`.  
4. Alice calls `claim()` → receives 1000 reward tokens. `accrued[alice]` stays at 1000.  
5. Alice calls `claim()` again → receives 1000 more. Repeat until the contract is empty.

**Fix:** Add `accrued[msg.sender] = 0;` before the transfer.

## Medium

### M-1 — `SafeTransferLib` silently succeeds when `token` has no code

**File:** `src/libraries/SafeTransferLib.sol`  
**Functions:** `safeTransfer()`, `safeTransferFrom()` (lines 14, 20)

**What an attacker can do:** If the token address ever points to an account with no deployed bytecode (e.g., token contract not yet deployed, or self-destructed), a low-level `call` returns `(true, "")`. `_succeeded("")` returns `true` because `data.length == 0`. The transfer is silently treated as successful while no tokens move.

**Conditions required:** The token address stored in an immutable must become a non-contract. This is low-probability in normal operation (immutable addresses are set at construction), but elevated in any deployment process where the token is deployed separately and the vault is funded before the token contract is confirmed, or if a token that uses `SELFDESTRUCT` is used. There is no contract-existence check to catch this.

**Fix:** Before executing the call, verify that `address(token).code.length > 0`.

### M-2 — `FixedPointMath.mulDiv` has no 512-bit intermediate; overflows cause DoS

**File:** `src/libraries/FixedPointMath.sol`  
**Function:** `mulDiv()` (line 14)

**What an attacker can do:** Cause `claim()`, `_pendingFor()`, or `notifyReward()` to revert for legitimate inputs, making rewards uncollectable.

**The issue:** The library computes `x * y / d` with a plain 256-bit multiply. Solidity 0.8.x reverts on overflow rather than wrapping, so correctness is preserved — but calls revert instead of returning the correct value.

In `_pendingFor`:
```solidity
return vault.balanceOf(account).mulDiv(delta, FixedPointMath.WAD);
```
If `balance * delta > type(uint256).max`, `claim()` and `claimable()` both revert. A large single holder combined with a large accumulated `delta` (i.e., many rewards distributed while supply is tiny) can push the product past the limit, making that holder's rewards permanently uncollectable without a protocol upgrade.

**Conditions required:** `balance * (globalIndex − userIndex) > 2²⁵⁶ − 1`. Achievable in practice when a single account holds a very large share balance and rewards are issued in large tranches relative to supply.

**Fix:** Use a full 512-bit `mulDiv` (e.g., OpenZeppelin `Math.mulDiv`) that avoids the overflow entirely.

## Informational

### I-1 — `nonReentrant` initialises from zero rather than one, costing extra gas

**Files:** `src/core/StakingVault.sol:59`, `src/rewards/RewardDistributor.sol:52`

Both use `uint256 private _entered` (default 0) and toggle between 0 and 1. The first call in each contract's lifetime writes a cold storage slot from 0 → 1 (20,000 gas SSTORE), then resets to 0 on exit. The standard pattern initialises the slot to 1 and toggles to 2 to keep the slot permanently warm (100 gas per subsequent check). This is not a security issue, but it inflates deployment and first-call gas costs unnecessarily.
