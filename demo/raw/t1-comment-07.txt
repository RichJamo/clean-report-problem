### [CRITICAL-1] Unbounded Reward Draining via Missing `accrued` Reset in `claim()`

**File:** `src/rewards/RewardDistributor.sol`  
**Function:** `claim()` (line 125)

**What an attacker can do:** Repeatedly call `claim()` to withdraw the same reward amount over and over until the contract's entire `rewardToken` balance is drained, receiving far more than they are entitled to.

**Conditions required:**
1. The attacker must have staked in `StakingVault` and had at least one reward notification (`notifyReward`) occur while their balance was non-zero.
2. The vault's `_checkpoint()` must have been triggered for the attacker's address at least once *after* a `notifyReward` — this happens automatically on every subsequent `deposit()` or `requestWithdrawal()` call.

**Root cause:** `claim()` computes `amount = accrued[msg.sender] + _pendingFor(msg.sender)` and correctly sets `userIndex[msg.sender] = globalIndex` (zeroing out the `_pendingFor` component), but **never clears `accrued[msg.sender]`**. On every subsequent call, `_pendingFor` returns 0 (index is current), but `accrued[msg.sender]` still holds the old settled amount and is paid out again.

```solidity
// claim() — line 125
function claim() external nonReentrant returns (uint256 amount) {
    amount = accrued[msg.sender] + _pendingFor(msg.sender);
    if (amount == 0) revert NothingToClaim();

    userIndex[msg.sender] = globalIndex;   // zeroes _pendingFor only
    totalClaimed += amount;

    rewardToken.safeTransfer(msg.sender, amount);
    // ❌ accrued[msg.sender] = 0; is MISSING
    emit Claimed(msg.sender, amount);
}
```

**Exploit scenario:**
1. Attacker deposits any amount → `userIndex[attacker] = 0`, `accrued[attacker] = 0`.
2. Owner calls `notifyReward(N)` → `globalIndex = N * WAD / supply`.
3. Attacker calls `deposit()` or `requestWithdrawal()` → vault calls `checkpoint(attacker)` → `accrued[attacker] = balance * globalIndex / WAD > 0`, `userIndex[attacker] = globalIndex`.
4. Attacker calls `claim()` → receives `accrued[attacker]` tokens. `userIndex` stays at `globalIndex`, so `_pendingFor` returns 0. **`accrued[attacker]` is NOT zeroed.**
5. Attacker calls `claim()` again → `amount = accrued[attacker] + 0 = accrued[attacker]` (same value). Transfers again.
6. Repeat step 5 until the contract's reward token balance is zero.

**Fix:** Add `accrued[msg.sender] = 0;` before (or after) the transfer in `claim()`.

### [MEDIUM-1] Unchecked Intermediate Multiplication in `FixedPointMath.mulDiv` Can Cause DoS

**File:** `src/libraries/FixedPointMath.sol`  
**Function:** `mulDiv()` (line 14)

**What an attacker can do:** In pathological but reachable conditions, arithmetic overflow in `x * y` causes a revert, making `deposit()`, `requestWithdrawal()`, `convertToShares()`, `convertToAssets()`, and `notifyReward()` permanently unusable.

**Conditions required:** Either (a) the product of two operands exceeds `2^256`, or (b) a privileged actor calls `notifyReward` with a large `amount` while `totalSupply` is near its minimum (1 wei), causing `globalIndex` to grow to a value where `balanceOf(account) * delta` overflows in `_pendingFor`.

```solidity
function mulDiv(uint256 x, uint256 y, uint256 d) internal pure returns (uint256) {
    return (x * y) / d;  // x * y can overflow uint256
}
```

Unlike OpenZeppelin's `Math.mulDiv`, which uses assembly to perform 512-bit intermediate multiplication, this implementation relies on Solidity 0.8.x overflow protection to revert rather than wrap. While overflow is impractical for normal token amounts, the function lacks the safety headroom that a production vault library should provide.

**Fix:** Replace with a 512-bit intermediate implementation (equivalent to OZ's `Math.mulDiv`), or add an explicit precondition check `require(y == 0 || x <= type(uint256).max / y)`.

### [LOW-1] Reentrancy Guard Writes to a Zero Slot on Every Call (Gas DoS Vector)

**File:** `src/core/StakingVault.sol` and `src/rewards/RewardDistributor.sol`  
**Modifier:** `nonReentrant`

**What an attacker can do:** There is no direct security exploit, but every call to a `nonReentrant` function pays ~20,000 gas for a cold `SSTORE` from 0 to 1, then resets back to 0. This increases transaction costs significantly and, in contracts with tight gas limits or in future EVM pricing changes, could cause well-formed transactions to run out of gas.

**Conditions required:** Any call to a `nonReentrant` function (e.g., `deposit`, `requestWithdrawal`, `completeWithdrawal`, `claim`, `notifyReward`).

```solidity
uint256 private _entered; // default: 0

modifier nonReentrant() {
    if (_entered == 1) revert Reentrancy();
    _entered = 1;   // SSTORE 0→1: 20,000 gas on every call
    _;
    _entered = 0;   // SSTORE 1→0: refund capped by EIP-3529
}
```

The standard pattern (OpenZeppelin, Solmate) initializes `_entered` to `1` in the constructor and toggles between `1` (not entered) and `2` (entered), making each SSTORE a warm non-zero-to-non-zero write (~2,900 gas each way).

**Fix:** Initialize `_entered = 1` in each constructor and use `2` as the entered sentinel, checking `if (_entered == 2) revert Reentrancy()`.

### [LOW-2] `transferOwnership` Accepts Zero Address, Silently Cancelling Pending Handovers

**File:** `src/auth/Ownable2Step.sol`  
**Function:** `transferOwnership()` (line 30)

**What an attacker can do:** A compromised or mistaken owner can call `transferOwnership(address(0))`, setting `pendingOwner = address(0)`. If ownership was previously being transferred to a legitimate nominee, that transfer is silently cancelled with no warning. The current owner retains control, but the nominee is dropped without notification.

**Conditions required:** The current owner calls `transferOwnership(address(0))` — by mistake or under duress.

```solidity
function transferOwnership(address newOwner) external onlyOwner {
    pendingOwner = newOwner;  // no zero-address check
    emit OwnershipTransferStarted(owner, newOwner);
}
```

**Fix:** Add `require(newOwner != address(0), "OWNER_ZERO")` consistent with the pattern used in constructors throughout the codebase.

### [INFORMATIONAL-1] Zero Cooldown Is Accepted Without Validation

**File:** `src/core/StakingVault.sol`  
**Function:** `constructor()` (line 89)

**What an attacker can do:** No direct attack. If the vault is deployed with `cooldown_ = 0`, the withdrawal queue provides no temporal separation between `requestWithdrawal` and `completeWithdrawal`. This eliminates any protection against same-block sandwich attacks around `accrueYield` (front-run deposit, yield notification, immediate withdrawal).

**Conditions required:** Deployer sets `cooldown_ = 0`.

**Fix:** Add `require(cooldown_ > 0, "COOLDOWN_ZERO")` in the `StakingVault` constructor, or document the zero-cooldown risk explicitly if intentional.
