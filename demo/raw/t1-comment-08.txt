## CRITICAL

### C-1 — `RewardDistributor.claim()` never zeroes `accrued`, enabling unlimited double-claiming

**File:** `src/rewards/RewardDistributor.sol`  
**Function:** `claim()` (line 125)

**What an attacker can do:** Call `claim()` repeatedly in separate transactions to drain the entire reward token balance of the contract, far beyond their actual entitlement.

**Root cause:** After transferring rewards, `accrued[msg.sender]` is never reset to zero. Only `userIndex[msg.sender]` is updated, which zeros out `_pendingFor` (the streaming component) but leaves the snapshot component intact:

```solidity
function claim() external nonReentrant returns (uint256 amount) {
    amount = accrued[msg.sender] + _pendingFor(msg.sender);
    if (amount == 0) revert NothingToClaim();

    userIndex[msg.sender] = globalIndex;   // zeros _pendingFor — correct
    totalClaimed += amount;

    rewardToken.safeTransfer(msg.sender, amount);
    // MISSING: accrued[msg.sender] = 0;
}
```

**Conditions required:**

1. The attacker has staked and has a non-zero `accrued[attacker]`. This balance is set when the vault calls `checkpoint` (which happens on every `deposit` or `requestWithdrawal`) while `_pendingFor(attacker) > 0` — i.e., rewards have been notified since the attacker's last checkpoint.
2. The attacker then calls `claim()`. Rewards are paid; `accrued` is not cleared.
3. Calling `claim()` again succeeds and transfers the same amount again. This loop continues until the contract's reward token balance is exhausted.

**Concrete exploit trace:**

```
Alice stakes 100 shares.
Owner notifies 40 ether in rewards → globalIndex = 0.4 WAD.
Alice calls vault.deposit(1) (any balance-mutating vault call triggers _checkpoint):
  → accrued[alice] = 100 * 0.4 WAD / WAD = 40 ether
  → userIndex[alice] = globalIndex
Alice calls claim():
  → amount = 40 + 0 = 40 ether transferred ✓
  → accrued[alice] still = 40 ether  (BUG)
Alice calls claim() again:
  → amount = 40 + 0 = 40 ether transferred again ✗
  → Repeat until contract is drained.
```

The bug also compounds at subsequent checkpoints. If the vault checkpoints Alice again (without her having claimed in between, or after a partial claim), the stale `accrued` value accumulates further:

```
accrued[alice] += _pendingFor(alice)  → adds new rewards on top of already-claimed amount
```

**Fix:** Add `accrued[msg.sender] = 0;` immediately before or after the `userIndex` update in `claim()`.

## MEDIUM

### M-1 — `deposit()` violates Checks-Effects-Interactions; incompatible with fee-on-transfer tokens

**File:** `src/core/StakingVault.sol`  
**Function:** `deposit()` (line 124)

**What an attacker can do:** This is not directly attacker-triggered, but it is a latent insolvency vulnerability. If the `asset` token charges a transfer fee (a common ERC-20 variant), the vault permanently overstates `totalAssets`, causing every future share price calculation to be wrong. Over time the vault cannot cover all withdrawals.

**Conditions required:** The asset token deducts a fee on `transferFrom`. The vault's `totalAssets` is updated before the transfer:

```solidity
totalAssets += assets;      // inflated by the full `assets`
totalSupply += shares;
balanceOf[msg.sender] += shares;

asset.safeTransferFrom(msg.sender, address(this), assets);  // only (assets - fee) arrives
```

Each deposit drives a growing gap between `totalAssets` (accounting) and the real balance. Early withdrawers receive more than their true share; later withdrawers find the vault insolvent.

For standard ERC-20s this ordering is safe (a failed `safeTransferFrom` reverts all state), but the contract contains no explicit guard against fee-on-transfer tokens, creating a foot-gun for integrators.

### M-2 — `FixedPointMath.mulDiv` uses naive `x * y` — overflow causes DoS for large values

**File:** `src/libraries/FixedPointMath.sol`  
**Function:** `mulDiv()` (line 14)

**What an attacker can do:** Certain combinations of large staked balances and a large accumulated `globalIndex` in `RewardDistributor` will cause the multiplication `balance * delta` to overflow, causing `claim()`, `claimable()`, and `checkpoint()` to revert for the affected account. The account's rewards become permanently unclaimable (stuck).

**Root cause:**

```solidity
function mulDiv(uint256 x, uint256 y, uint256 d) internal pure returns (uint256) {
    return (x * y) / d;   // overflows if x * y >= 2^256
}
```

Solidity 0.8.x treats this as a checked operation: the multiplication reverts on overflow instead of wrapping. A 512-bit intermediate (as used in OpenZeppelin's `Math.mulDiv`) would avoid this.

**Conditions required:** `balance * (globalIndex - userIndex[account])` ≥ 2²⁵⁶. For 18-decimal tokens, this requires `balance ≈ 1e30` tokens and a sufficiently large index delta — achievable in high-supply or long-running deployments, or by a griefer who notifies many small rewards to drive up `globalIndex` while a whale's `userIndex` is stale.

## LOW

### L-1 — `setGuardian()` accepts the zero address, silently removing the guardian role

**File:** `src/core/StakingVault.sol`  
**Function:** `setGuardian()` (line 201)

**What an attacker can do:** Not directly attacker-triggered. If the owner accidentally calls `setGuardian(address(0))`, the guardian fast-pause capability is silently eliminated. Emergency response time increases to however long the owner's key takes to sign, which may matter during an active exploit.

**Conditions:** Owner error or key compromise leading to the call `setGuardian(address(0))`.

**Fix:** Add `require(newGuardian != address(0), "GUARDIAN_ZERO");` or an equivalent revert.

---

### L-2 — `transferOwnership()` accepts the zero address as `pendingOwner`

**File:** `src/auth/Ownable2Step.sol`  
**Function:** `transferOwnership()` (line 30)

**What an attacker can do:** Not directly exploitable. If the owner sets `pendingOwner = address(0)`, `acceptOwnership()` can never be called (address(0) cannot sign transactions), so the pending transfer is silently voided. The current owner retains control, but the intent to transfer is obscured and the `OwnershipTransferStarted` event is misleading.

**Fix:** Add `require(newOwner != address(0), "OWNER_ZERO");` to `transferOwnership()`.
