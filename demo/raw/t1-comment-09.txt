## CRITICAL-1 — `claim()` Never Zeroes `accrued[msg.sender]`, Enabling Unlimited Reward Drain

**File:** `src/rewards/RewardDistributor.sol`  
**Function:** `claim()` — lines 125–135

**What an attacker can do:**  
Call `claim()` in an unbounded loop to drain the entire reward token balance of the distributor. Each call transfers the same `accrued[msg.sender]` value because that storage slot is read but never cleared.

**Root cause:**  
After paying out rewards, `accrued[msg.sender]` is never reset to zero. `userIndex[msg.sender] = globalIndex` is set (line 129), so `_pendingFor` correctly returns 0 on all subsequent calls. However, `accrued[msg.sender]` retains its old value, so `amount = accrued[msg.sender] + 0` is non-zero on every future call, bypassing the `NothingToClaim` guard.

**Conditions required:**  
The attacker must first have a non-zero `accrued` balance. This happens through the normal user flow:
1. Attacker stakes while the vault has an active `rewardDistributor`.
2. Owner calls `notifyReward`, advancing `globalIndex`.
3. Attacker calls `deposit()` or `requestWithdrawal()` — either triggers `_checkpoint`, which writes pending rewards into `accrued[attacker]` and resets the attacker's `userIndex` to `globalIndex`.

After step 3, `accrued[attacker] > 0` and `_pendingFor(attacker) == 0`. Every subsequent `claim()` call re-transfers `accrued[attacker]` indefinitely.

**Proof of concept (pseudocode):**
```
stake(100)
notifyReward(100)          // globalIndex = 1e18; attacker has 100 pending
deposit(1)                 // checkpoint: accrued[attacker] = 100, userIndex = globalIndex
claim()                    // pays 100; accrued[attacker] is still 100
claim()                    // pays 100 again  <-- repeats until distributor is empty
```

**Fix:** Add `accrued[msg.sender] = 0;` before or immediately after reading the amount.

## HIGH-2 — Check-Effects-Interactions Violation in `deposit()` — State Updated Before Token Transfer

**File:** `src/core/StakingVault.sol`  
**Function:** `deposit()` — lines 124–139

**What an attacker can do:**  
If the staked asset is a reentrant token (ERC-777, ERC-1363, or any token that issues a callback on transfer), the token's sender hook fires after `totalAssets`, `totalSupply`, and `balanceOf[msg.sender]` have been updated but before the tokens have actually arrived. During this window, the vault's accounting overstates its holdings. The vault's own `nonReentrant` guard blocks re-entry into vault write functions, but `RewardDistributor.claim()` has its own separate `_entered` slot and is freely callable from the hook. Combined with CRITICAL-1, an attacker using a hooking token could trigger `claim()` from inside the hook to compound the drain.

The same violation exists in `accrueYield()` (lines 183–191), where `totalAssets` is incremented before `safeTransferFrom` executes.

**Conditions required:**  
The staked `asset` must be a token type that issues callbacks (ERC-777 hooks or ERC-1363 `transferFromAndCall`). Standard ERC-20 tokens are not affected.

**Fix:** Perform the external token transfer before updating any state, or use a pattern where the vault checks its balance delta after the transfer.

## MEDIUM-1 — No Minimum Shares (Slippage) Parameter in `deposit()`

**File:** `src/core/StakingVault.sol`  
**Function:** `deposit()` — line 124

**What an attacker can do:**  
Front-run the owner's `accrueYield()` transaction. A watcher observing the mempool can:
1. See a pending `accrueYield(N)` transaction.
2. Submit `deposit(M)` with higher gas, buying shares at the pre-accrual price.
3. After `accrueYield` executes, those shares are immediately worth more.
4. Submit `requestWithdrawal` and wait out the cooldown to pocket the gain.

Legitimate depositors who sent transactions expecting the current share price may receive fewer shares than anticipated if `accrueYield` is sandwiched in front of them.

**Conditions required:**  
Attacker can see the `accrueYield` transaction in the mempool before it is mined (standard on any public network). Cooldown period must elapse before profit is realized.

**Fix:** Add a `minShares` parameter to `deposit()` that reverts if the minted shares fall below the caller's threshold.

## MEDIUM-2 — `FixedPointMath.mulDiv` Uses Naive `x * y`, Reverts on Overflow

**File:** `src/libraries/FixedPointMath.sol`  
**Functions:** `mulDiv()` — line 14; `mulDivUp()` — line 20

**What an attacker can do:**  
For any pair `(x, y)` where `x * y > type(uint256).max`, the operation reverts due to Solidity 0.8.x overflow checking. This makes the following operations revert for sufficiently large values:
- `convertToShares` / `convertToAssets` in the vault
- `_pendingFor` in the distributor (large balance × large index delta)
- `notifyReward` (large amount × WAD)

An attacker with significant holdings, or in a vault with very high TVL and many reward cycles, could trigger this DoS by depositing enough to make `balance * globalIndex > type(uint256).max` in `_pendingFor`.

**Conditions required:**  
Realistic overflow thresholds are very large (product of balance and WAD must exceed ~1.16 × 10^77), but can be approached in long-running protocols with many `notifyReward` calls accumulating a high `globalIndex`.

**Fix:** Replace the naive multiply with a 512-bit intermediate multiply-then-divide (e.g., Uniswap v3's `FullMath.mulDiv`).

## LOW-3 — Pre-Distributor Depositors Receive Retroactive Rewards From Index Zero

**File:** `src/core/StakingVault.sol` / `src/rewards/RewardDistributor.sol`  
**Function:** `setRewardDistributor()` (vault, line 194); `_pendingFor()` (distributor, line 140)

**What an attacker can do:**  
Users who stake before `setRewardDistributor` is called have `userIndex[account] = 0`. When `notifyReward` is first called, `globalIndex` becomes `N`. Those early stakers then see `_pendingFor = balance * (N - 0) / WAD`, earning rewards as if they had been in since the contract's genesis. A sophisticated user who observes the vault deployed with no distributor yet can stake a large position cheaply, then claim disproportionate rewards once the distributor is wired and funded.

**Conditions required:**  
`setRewardDistributor` is called after the first `notifyReward` period, or at minimum after users have already deposited. This is the described intended deployment sequence ("Set once, after deployment"), making it an inherent window.

**Fix:** Either initialize `userIndex[account]` to the current `globalIndex` in the distributor's constructor (if globalIndex is 0 this is a no-op), or call `setRewardDistributor` before any deposits are accepted.
