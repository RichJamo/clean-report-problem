## CRITICAL-1 — Reward tokens drainable via repeated `claim()` calls

**File:** `src/rewards/RewardDistributor.sol`  
**Function:** `claim()` (line 125)

### What an attacker can do

Any account that has ever had `checkpoint()` called on it with a non-zero pending amount can call `claim()` in a tight loop and drain the entire reward token balance of `RewardDistributor`, receiving the same stale `accrued` value on every call.

### Root cause

`claim()` computes `amount = accrued[msg.sender] + _pendingFor(msg.sender)`, updates `userIndex[msg.sender] = globalIndex`, and transfers `amount` — but **never resets `accrued[msg.sender]` to zero**.

```solidity
// RewardDistributor.sol:125-134
function claim() external nonReentrant returns (uint256 amount) {
    amount = accrued[msg.sender] + _pendingFor(msg.sender);
    if (amount == 0) revert NothingToClaim();

    userIndex[msg.sender] = globalIndex;   // index synced …
    totalClaimed += amount;

    rewardToken.safeTransfer(msg.sender, amount);
    // ← accrued[msg.sender] is never set to 0
    emit Claimed(msg.sender, amount);
}
```

After the first call, `userIndex[msg.sender] == globalIndex`, so `_pendingFor()` returns 0 on every subsequent call. However, `accrued[msg.sender]` retains its prior value, so `amount` is non-zero and the `NothingToClaim` guard is bypassed on every subsequent call.

### Conditions required

1. At some point between two `notifyReward` calls the attacker's share balance must have changed (depositing more or requesting a withdrawal), which causes the vault to call `distributor.checkpoint(attacker)`. That call sets `accrued[attacker]` to the pending entitlement and syncs `userIndex`.
2. The attacker then calls `claim()` repeatedly. Each call pays out `accrued[attacker]` again until the distributor's reward token balance is exhausted.

### Proof-of-concept trace

```
Alice stakes 100 ether.
notifyReward(50 ether)  →  globalIndex = 0.5e18

Alice calls deposit(1)  →  vault calls distributor.checkpoint(Alice):
    pending = 100e18 * (0.5e18 − 0) / 1e18 = 50 ether
    accrued[Alice] = 50 ether
    userIndex[Alice] = 0.5e18

Alice calls claim() #1:
    _pendingFor(Alice) = 0   (userIndex == globalIndex)
    amount = 50 ether + 0 = 50 ether  ✓
    userIndex[Alice] = 0.5e18 (unchanged)
    accrued[Alice]   = 50 ether (UNCHANGED — bug)
    → 50 ether transferred

Alice calls claim() #2:
    amount = 50 ether + 0 = 50 ether  ✓  (same!)
    → 50 ether transferred again

… repeats until distributor balance is zero.
```

### Fix

Add `accrued[msg.sender] = 0;` before (or immediately after) the transfer in `claim()`:

```solidity
accrued[msg.sender] = 0;
userIndex[msg.sender] = globalIndex;
totalClaimed += amount;
rewardToken.safeTransfer(msg.sender, amount);
```

## MEDIUM-1 — Fee recipient resolved at settlement time can permanently DoS in-flight withdrawals

**File:** `src/core/StakingVault.sol`  
**Function:** `completeWithdrawal()` (line 166)

### What an attacker can do

The `FeeController` owner can set `feeRecipient` to an address that is unable to receive the asset token (a reverting contract, a token-blacklisted address, or `address(0)` — though that last case is blocked). Any user whose queued withdrawal carries a non-zero `feeBps` snapshot will then be permanently unable to call `completeWithdrawal`, because the fee transfer reverts and rolls back the entire settlement.

```solidity
// StakingVault.sol:172-174
if (fee != 0) {
    asset.safeTransfer(feeController.feeRecipient(), fee);  // ← resolved fresh
}
```

The fee **rate** (`feeBps`) is correctly snapshotted in the `Request` struct at the time `requestWithdrawal` is called. The fee **recipient** is not — it is read from `FeeController` at settlement time. The vault owner cannot rescue affected users unilaterally: even setting `withdrawalFeeBps = 0` in `FeeController` does not help, because the snapshot in the `Request` struct already holds the old non-zero rate.

### Conditions required

1. `FeeController` owner (who may differ from the `StakingVault` owner) sets `feeRecipient` to a broken address after users have submitted withdrawal requests with non-zero fees.
2. Those users can no longer call `completeWithdrawal`. Their assets are locked until the `FeeController` owner restores a working recipient.

This is especially relevant for asset tokens with blacklists (USDC, USDT), where Circle/Tether can unilaterally blacklist the fee recipient after requests are in flight.

### Fix

Either (a) snapshot the fee recipient in the `Request` struct alongside `feeBps`, or (b) implement a pull-payment pattern for fees (record the owed fee in storage, let the recipient withdraw separately) so that a broken recipient cannot block the user's own payout.

## LOW-1 — CEI violation in `deposit()`: state updated before external token transfer

**File:** `src/core/StakingVault.sol`  
**Function:** `deposit()` (line 124)

`totalAssets`, `totalSupply`, and `balanceOf[msg.sender]` are all incremented before `asset.safeTransferFrom` is called. If the token's `transferFrom` returns `true` but actually transfers fewer tokens than requested (fee-on-transfer tokens), the vault's accounting permanently diverges from its actual balance, inflating the share price and leaving the last withdrawers short.

The `nonReentrant` guard prevents the more acute re-entrancy exploit, but the CEI inversion still makes the contract incompatible with fee-on-transfer tokens in a silent, irrecoverable way. Standard practice is to measure the real balance delta after the transfer and use that as the credited amount.

## LOW-2 — `FixedPointMath.mulDiv` uses unchecked intermediate product

**File:** `src/libraries/FixedPointMath.sol`  
**Function:** `mulDiv()` (line 14)

```solidity
function mulDiv(uint256 x, uint256 y, uint256 d) internal pure returns (uint256) {
    return (x * y) / d;   // x * y can overflow
}
```

Solidity 0.8.x panics (reverts) on overflow, so this cannot silently corrupt state. However, it can cause a DoS revert in `convertToShares`, `convertToAssets`, `_pendingFor`, and `notifyReward` if both operands are sufficiently large. Replace with a 512-bit intermediate multiply (as used in OpenZeppelin's `Math.mulDiv`) to remove the revert surface entirely.

## LOW-3 — Cooldown is immutable and unbounded

**File:** `src/core/WithdrawalQueue.sol`  
**Constructor** (line 50); configured via `StakingVault` constructor (line 101)

`cooldown` is stored as an immutable `uint64`. There is no upper-bound check at deployment time, so an operator error (e.g., passing seconds instead of the intended unit, or simply a large value) could lock user funds for years with no administrative remedy. Add a maximum cooldown constant and enforce it in the constructor.

## Out of scope / informational

- **`Ownable2Step.transferOwnership` accepts `address(0)`** as `pendingOwner`. Because no account can call `acceptOwnership` from `address(0)`, the effect is that the pending transfer is silently abandoned rather than ownership being renounced. Low impact; a zero-address check would make intent explicit.
- **Guardian griefing via repeated pauses**: the guardian can pause the vault each time the owner unpauses it. The owner can defuse this by calling `setGuardian(address(0))`, so no additional control is needed, but the trust model should be documented.
- **`totalClaimed` accounting**: `totalClaimed` is incremented in `claim()` even for the duplicate payouts described in CRITICAL-1, meaning it over-reports paid rewards. This makes on-chain accounting unreliable as a forensic tool after an exploit.
