## CRITICAL — C-1: `RewardDistributor.claim()` never clears `accrued`, enabling unlimited replay

**File:** `src/rewards/RewardDistributor.sol`  
**Function:** `claim()` (line 119)

### What an attacker can do

An attacker who has any non-zero value in `accrued[attacker]` can call `claim()` in a loop and drain the entire reward token balance of the contract. Each call transfers the same `accrued` amount again because it is never zeroed out.

### Vulnerable code

```solidity
function claim() external nonReentrant returns (uint256 amount) {
    amount = accrued[msg.sender] + _pendingFor(msg.sender);
    if (amount == 0) revert NothingToClaim();

    userIndex[msg.sender] = globalIndex;   // ← updates pending tracking
    totalClaimed += amount;

    rewardToken.safeTransfer(msg.sender, amount);  // ← transfers accrued + pending

    emit Claimed(msg.sender, amount);
    // BUG: accrued[msg.sender] is never set to 0
}
```

`userIndex[msg.sender] = globalIndex` only prevents re-spending of the *pending* portion. The `accrued[msg.sender]` mapping is populated by `checkpoint()` and is never cleared by `claim()`.

### Step-by-step exploit

1. Attacker stakes before any `notifyReward` call.
2. Owner calls `notifyReward(X)` — `globalIndex` advances.
3. Attacker deposits again or calls `requestWithdrawal`, triggering `_checkpoint`. This writes `accrued[attacker] = Y` (e.g. 75 ether).
4. Attacker calls `claim()`:
   - `amount = 75 + 0 = 75`; 75 tokens transferred; `accrued[attacker]` **still = 75**.
5. Attacker calls `claim()` again:
   - `amount = 75 + 0 = 75`; 75 more tokens transferred.
6. Repeat until the contract is empty.

The reentrancy guard on `claim()` is irrelevant — the exploit requires only sequential calls and succeeds without any reentrancy.

### Conditions required

- Attacker must have staked before at least one `notifyReward` call.
- Attacker must trigger one `checkpoint` (any deposit or withdrawal request achieves this).
- The contract must hold reward tokens (it always does, by design).

### Fix

Add `accrued[msg.sender] = 0;` before or after the transfer in `claim()`.

## HIGH — H-1: `FixedPointMath.mulDiv()` uses naive multiplication that overflows for large inputs, creating a permanent DoS

**File:** `src/libraries/FixedPointMath.sol`  
**Function:** `mulDiv()` (line 14)

### What an attacker can do

An attacker or adverse market condition can cause certain accounts to be permanently unable to claim rewards, deposit, or request withdrawals, because the intermediate product `x * y` overflows `uint256` and Solidity 0.8 reverts.

### Vulnerable code

```solidity
function mulDiv(uint256 x, uint256 y, uint256 d) internal pure returns (uint256) {
    return (x * y) / d;   // x * y can overflow uint256
}
```

This is called in several critical paths:

- `RewardDistributor._pendingFor()`: `vault.balanceOf(account).mulDiv(delta, WAD)` — overflows when `balance * indexDelta > 2^256`.
- `RewardDistributor.notifyReward()`: `amount.mulDiv(WAD, supply)` — overflows when `amount > ~1.16 × 10^59` (not a realistic concern for most tokens).
- `StakingVault.convertToShares()` and `convertToAssets()`: overflow possible when `assets * supply` exceeds `2^256`.

The reward distributor path is the most dangerous. If `globalIndex` grows large (through many `notifyReward` calls) and a staker has not claimed for a long period, `balance * (globalIndex - userIndex)` can exceed `2^256`. At that point, the user's `claim()` reverts permanently — their accumulated rewards are frozen.

### Conditions required

- A staker holds a large share balance *and* goes a long time without checkpointing while `globalIndex` is advanced many times.
- No single `notify` call needs to be large; the cumulative delta is what matters.

### Fix

Replace `mulDiv` with a full 512-bit intermediate implementation (e.g., the Mulmod technique used in OpenZeppelin's `Math.mulDiv`), which avoids the intermediate overflow entirely.

## MEDIUM — M-1: `StakingVault.deposit()` makes an external call to the reward distributor before the reentrancy lock can isolate state, creating cross-contract reentrancy surface

**File:** `src/core/StakingVault.sol`  
**Function:** `deposit()` (line 124)

### What an attacker can do

If the owner ever replaces or upgrades the `rewardDistributor` to a malicious or buggy contract (noting that `setRewardDistributor` is callable only once, so this applies if the first-set distributor is adversarial), the distributor's `checkpoint` implementation executes with the reentrancy lock held on the vault, but *before* the share balance state is written. The malicious distributor can observe a stale balance, emit incorrect events, or revert the entire deposit.

More practically: because `_checkpoint` is an external call occurring before `balanceOf[msg.sender]` is updated, any future integration that is authorized to call `checkpoint` externally can observe the vault in an inconsistent mid-deposit state.

### Code path

```solidity
function deposit(uint256 assets) external nonReentrant whenNotPaused returns (uint256 shares) {
    _checkpoint(msg.sender);         // external call — state not yet updated
    shares = convertToShares(assets);
    totalAssets += assets;           // state written after the external call
    totalSupply += shares;
    balanceOf[msg.sender] += shares;
    asset.safeTransferFrom(...);
}
```

### Conditions required

- The `rewardDistributor` is a contract under attacker control, or a third-party contract with a hook.
- Since `setRewardDistributor` is callable once, this is most dangerous at deployment time if the initial distributor is malicious.

### Note

The vault's reentrancy guard mitigates direct re-entry back into vault functions during `_checkpoint`. This is therefore medium severity rather than high.

## LOW — L-1: `WithdrawalQueue.enqueue()` performs an unchecked cast of `block.timestamp` to `uint64`

**File:** `src/core/WithdrawalQueue.sol`  
**Function:** `enqueue()` (line 75)

### What an attacker can do

No practical exploit today, but the pattern is unsafe. An explicit cast in Solidity 0.8 does **not** check for truncation — only arithmetic operations do. If `block.timestamp` ever exceeds `type(uint64).max` (≈ year 584,942), the truncated value produces a wildly wrong `unlockAt`, potentially making withdrawals immediately available.

```solidity
uint64 unlockAt = uint64(block.timestamp) + cooldown;
//                 ^^^^^^^^^^^^^^^^^^^^ silent truncation, not checked
```

### Conditions required

- `block.timestamp > type(uint64).max` (not reachable in any foreseeable future, but the code pattern is wrong).

### Fix

Use `SafeCast` or an explicit bounds check before casting.

## LOW — L-2: `StakingVault.setGuardian()` accepts `address(0)`, silently removing the guardian without acknowledgement

**File:** `src/core/StakingVault.sol`  
**Function:** `setGuardian()` (line 201)

### What an attacker can do

Not an attacker vector — this requires the owner. However, an owner key compromise or governance mistake can call `setGuardian(address(0))`, permanently removing the emergency pause capability until `setGuardian` is called again with a real address. There is no warning, no event with a clear "guardian removed" semantic, and no confirmation.

```solidity
function setGuardian(address newGuardian) external onlyOwner {
    emit GuardianUpdated(guardian, newGuardian);
    guardian = newGuardian;   // no zero-address check
}
```

### Conditions required

- Owner calls `setGuardian(address(0))` (accidentally or under duress).

### Fix

Add `require(newGuardian != address(0), "GUARDIAN_ZERO")` or reuse the `ZeroAddress` / `ZeroAmount` error pattern already in use.

## INFORMATIONAL — I-1: `WithdrawalCompleted` event emits net amount (`paid`) in the field named `assets`

**File:** `src/core/StakingVault.sol`  
**Function:** `completeWithdrawal()` (line 176)

The event is declared as:
```solidity
event WithdrawalCompleted(address indexed account, uint256 indexed id, uint256 assets, uint256 fee);
```

But the call passes `paid` (already net of the fee) in the `assets` position:
```solidity
emit WithdrawalCompleted(msg.sender, id, paid, fee);
```

Off-chain indexers computing `paid + fee` to verify the gross amount will get the wrong answer. Consider emitting the original `assets` (gross) amount and keeping `paid` and `fee` alongside it, or renaming the field to `amountPaid`.
