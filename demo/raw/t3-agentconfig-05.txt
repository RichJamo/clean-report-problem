## Finding 1 — CRITICAL: `RewardDistributor.claim()` Never Zeroes `accrued[msg.sender]`

**File**: `src/rewards/RewardDistributor.sol`
**Function**: `claim()` (lines 119–129)

### What an attacker can do

After a user's `accrued` balance has been populated, they can call `claim()` in a loop across multiple transactions and extract that same amount each time, draining the entire reward token balance held by `RewardDistributor`.

### Root cause

```solidity
function claim() external nonReentrant returns (uint256 amount) {
    amount = accrued[msg.sender] + _pendingFor(msg.sender);
    if (amount == 0) revert NothingToClaim();

    userIndex[msg.sender] = globalIndex;   // prevents future _pendingFor accrual
    totalClaimed += amount;

    rewardToken.safeTransfer(msg.sender, amount);
    // ← accrued[msg.sender] is never cleared
}
```

`userIndex[msg.sender]` is updated so `_pendingFor` returns 0 on subsequent calls. But `accrued[msg.sender]` retains its previous value, so on every subsequent call:

```
amount = accrued[msg.sender]   // still the old, non-zero value
        + _pendingFor(...)      // 0 (index already up to date)
```

The `NothingToClaim` guard never triggers and the transfer succeeds each iteration.

### Conditions required

1. The vault must have called `checkpoint()` for the attacker while `globalIndex > userIndex[attacker]`. This happens on any `deposit()` or `requestWithdrawal()` call made after at least one `notifyReward()`.
2. `RewardDistributor` must hold sufficient reward tokens (which it always does after legitimate reward notifications).

### Concrete attack path

1. Alice stakes 100 tokens. (`accrued[Alice] = 0`, `userIndex[Alice] = 0`)
2. Owner calls `notifyReward(100)`. `globalIndex` rises to `1e18`.
3. Alice stakes 1 more token. The vault calls `checkpoint(Alice)`:
   - `pending = 100 * (1e18 − 0) / 1e18 = 100`
   - `accrued[Alice] += 100` → **`accrued[Alice] = 100`**
   - `userIndex[Alice] = globalIndex`
4. Alice calls `claim()`: receives 100 reward tokens. **`accrued[Alice]` remains 100.**
5. Alice calls `claim()` again: `amount = 100 + 0 = 100`. Receives 100 more tokens.
6. Repeat until `RewardDistributor` is empty.

**Fix**: Add `accrued[msg.sender] = 0;` before or immediately after computing `amount`.

## Finding 2 — MEDIUM: `feeRecipient` Is Read at Completion Time, Not Locked at Request Time

**File**: `src/core/StakingVault.sol`
**Function**: `completeWithdrawal()` (lines 166–178)

### What an attacker can do

The owner of `FeeController` can brick all pending non-zero-fee withdrawal requests by changing `feeRecipient` to a contract whose `transfer` hook reverts. Users in the cooldown queue would be unable to retrieve their assets.

### Root cause

`requestWithdrawal()` correctly locks the `feeBps` rate in the queue at request time (`WithdrawalQueue.sol:159`). However, `completeWithdrawal()` fetches the recipient live:

```solidity
asset.safeTransfer(feeController.feeRecipient(), fee);   // recipient not locked
asset.safeTransfer(msg.sender, paid);
```

If `feeRecipient()` returns an address whose fallback reverts (e.g., a broken multisig or a purposefully malicious contract), `safeTransfer` propagates the revert, blocking the entire completion.

### Conditions required

- One or more withdrawal requests are queued with `feeBps > 0` (zero-fee requests skip the fee transfer entirely via the `if (fee != 0)` guard).
- The owner changes `feeRecipient` to a contract that reverts on ERC-20 receipt after those requests were created.

Note: `FeeController.setFeeRecipient` prevents `address(0)` but imposes no other restriction on the recipient.

## Finding 3 — MEDIUM: No Minimum Cooldown Enforced at Deployment

**File**: `src/core/StakingVault.sol` constructor (lines 89–102); `src/core/WithdrawalQueue.sol` constructor (lines 50–54)

### What an attacker can do

With `cooldown_ = 0` the queue's unlock time equals the block timestamp at enqueue, so `block.timestamp < request.unlockAt` is immediately false. `requestWithdrawal` and `completeWithdrawal` can be called back-to-back in the same block, making the exit queue a no-op.

### Conditions required

- The deployer passes `cooldown_ = 0` (or a trivially small value) to the `StakingVault` constructor. There is no on-chain guard preventing it.

### Impact

Stakers can deposit, withdraw, and collect rewards without any time commitment to the vault, diluting the economic incentive for honest long-term stakers and potentially enabling block-level reward harvesting when combined with Finding 7.

## Finding 4 — MEDIUM: Fee-on-Transfer Asset Inflates `totalAssets`

**File**: `src/core/StakingVault.sol`
**Functions**: `deposit()` (lines 124–139), `accrueYield()` (lines 183–191)

### What an attacker can do

If the staked `asset` charges a transfer fee, the vault receives fewer tokens than the amount it credits to `totalAssets`. Over time, `totalAssets` diverges above the actual token balance. Early withdrawers can drain the vault's real balance, leaving later withdrawers unable to complete their withdrawals.

### Root cause

Both functions update accounting using the requested amount, then call `safeTransferFrom` without checking the post-transfer balance:

```solidity
totalAssets += assets;                                        // accounting
asset.safeTransferFrom(msg.sender, address(this), assets);   // actual transfer (may be less)
```

### Conditions required

- The `asset` token is deployed with a fee-on-transfer mechanism (e.g., a deflationary or tax token).
- The contract does not verify the received amount equals `assets`.

## Finding 5 — LOW: `guardian` Accepts `address(0)` Without Warning

**File**: `src/core/StakingVault.sol`
**Functions**: `constructor()` (line 100), `setGuardian()` (lines 201–204)

### What an attacker can do

Silently disable the guardian emergency-pause role. There is no zero-address guard on `initialGuardian` in the constructor or on `newGuardian` in `setGuardian()`. Setting guardian to `address(0)` leaves only the owner able to pause—contradicting the design intent of a faster-acting pause path.

### Conditions required

- Deployer supplies `address(0)` as `initialGuardian`, or owner calls `setGuardian(address(0))`.

Compare: the constructor validates `asset` and `feeController` against zero but not `guardian`.

## Finding 6 — LOW: `Ownable2Step.transferOwnership` Accepts `address(0)` as Nominee

**File**: `src/auth/Ownable2Step.sol`
**Function**: `transferOwnership()` (lines 30–33)

### What an attacker can do

Accidentally cancel a pending ownership transfer. Calling `transferOwnership(address(0))` sets `pendingOwner = address(0)` and emits an `OwnershipTransferStarted` event with the zero address. Any previously nominated owner can no longer call `acceptOwnership()` without the current owner issuing a correcting call. An inattentive operator could mistake this for a valid nomination.

### Conditions required

- Owner accidentally passes `address(0)` to `transferOwnership()`.

## Finding 7 — INFORMATIONAL: `mulDiv` Reverts on Inputs Whose Product Exceeds `uint256`

**File**: `src/libraries/FixedPointMath.sol`
**Function**: `mulDiv()` (lines 14–16)

```solidity
function mulDiv(uint256 x, uint256 y, uint256 d) internal pure returns (uint256) {
    return (x * y) / d;  // intermediate product can overflow
}
```

Solidity 0.8.x reverts on overflow, so there is no silent wrapping. However, unlike OpenZeppelin's `Math.mulDiv` (which uses 512-bit intermediate arithmetic), this implementation will revert whenever `x * y > type(uint256).max`. The revert would DoS `convertToShares`, `convertToAssets`, and the reward index calculation for any realistic combination of large `totalAssets` and `totalSupply` approaching `10^38`. This is unlikely with normal token supplies but limits composability with high-decimal or high-supply tokens.

## Finding 8 — INFORMATIONAL: Reward Sandwiching via `notifyReward` Front-Running

**File**: `src/rewards/RewardDistributor.sol`
**Function**: `notifyReward()` (lines 103–115)

### What an attacker can do

An attacker who observes a pending `notifyReward` transaction in the mempool can front-run it with a large `deposit()`, earning a disproportionate share of that reward batch relative to their actual staking duration. They then immediately back-run with `requestWithdrawal()`.

### Conditions required

- A public mempool where `notifyReward` is visible before inclusion.
- Sufficient capital to materially shift the `totalSupply` weight.

### Limiting factors

The cooldown period and withdrawal fee (up to 5%) cap the attacker's profit and mean the capital is locked for the duration. With a meaningful cooldown (e.g., 7 days) and non-zero fee the economics are unfavorable unless reward batches are very large. This is an economic inefficiency rather than a fund-loss exploit, but it directly erodes rewards for honest long-term stakers.
