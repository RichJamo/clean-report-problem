# Security Audit Report — Staking Vault

**Scope:** `src/core/StakingVault.sol`, `src/core/FeeController.sol`, `src/core/WithdrawalQueue.sol`, `src/rewards/RewardDistributor.sol`, `src/auth/Ownable2Step.sol`, `src/libraries/`

## [CRITICAL] RewardDistributor — `accrued` balance is never zeroed on claim

**File:** `src/rewards/RewardDistributor.sol`  
**Function:** `claim()` (line 119)

**What an attacker can do:** Any account that has a non-zero `accrued` balance can call `claim()` in an unlimited loop of separate transactions to drain every reward token held by the `RewardDistributor`.

**Conditions required:** The account must have had `accrued[account]` set to a non-zero value by a prior call to `checkpoint()` (which the vault calls automatically before any balance change on deposit or withdrawal request). After that, no further staking is required.

**Root cause:** The function calculates the total claimable amount and transfers it, but never writes `accrued[msg.sender] = 0`:

```solidity
function claim() external nonReentrant returns (uint256 amount) {
    amount = accrued[msg.sender] + _pendingFor(msg.sender);
    if (amount == 0) revert NothingToClaim();

    userIndex[msg.sender] = globalIndex;   // syncs pending to 0
    totalClaimed += amount;

    rewardToken.safeTransfer(msg.sender, amount);   // accrued[] still unchanged
    // accrued[msg.sender] is never reset!
}
```

After the first call, `userIndex[msg.sender] == globalIndex`, so `_pendingFor` returns 0. But `accrued[msg.sender]` still holds the original value. Every subsequent call reads the same stale `accrued` amount, passes the `NothingToClaim` guard, and transfers again. The reentrancy guard prevents doing this within a single transaction, but ordinary sequential transactions across multiple blocks work without restriction.

**Example:** Alice stakes, earns 40 tokens via `notifyReward`, gets checkpointed. She calls `claim()` once per block indefinitely, receiving 40 tokens each time until the contract balance is zero.

**Fix:** Add `accrued[msg.sender] = 0;` before the transfer.

## [MEDIUM] StakingVault — `deposit()` violates Checks-Effects-Interactions

**File:** `src/core/StakingVault.sol`  
**Function:** `deposit()` (line 124)

**What an attacker can do:** With a staking asset that calls a hook on the sender or receiver during `transferFrom` (e.g., an ERC-777-compatible token), the vault's state is already mutated when the external code runs: `totalAssets`, `totalSupply`, and `balanceOf[msg.sender]` reflect the new shares, but the tokens have not yet arrived. A malicious token or a hook-bearing token could observe inflated share accounting, and non-`nonReentrant`-guarded entry points (`pause`, `setGuardian`) are reachable from within that hook.

**Conditions required:** The staking asset must support transfer hooks or callbacks that fire mid-`transferFrom`. Standard ERC-20 tokens without hooks are unaffected.

**Root cause:**

```solidity
// Effects — state written first
totalAssets += assets;
totalSupply += shares;
balanceOf[msg.sender] += shares;

// Interaction — tokens arrive after
asset.safeTransferFrom(msg.sender, address(this), assets);
```

The `nonReentrant` modifier protects all write paths (`deposit`, `requestWithdrawal`, `accrueYield`, `completeWithdrawal`), so the practical attack surface is narrow. The finding is recorded because the pattern violates the safe ordering, and its safety depends entirely on the reentrant guard and the token implementation.

**Fix:** Move the `safeTransferFrom` before the state updates, or keep effects last and ensure the token is guaranteed to be a plain ERC-20.

## [MEDIUM] StakingVault / WithdrawalQueue — zero cooldown is accepted, allowing instant withdrawal

**File:** `src/core/StakingVault.sol` constructor (line 89); `src/core/WithdrawalQueue.sol` constructor (line 50)

**What an attacker can do:** If the vault is deployed with `cooldown_ = 0`, an external contract can call `requestWithdrawal` and `completeWithdrawal` back-to-back in the same transaction: after `requestWithdrawal` returns, `_entered` is reset to 0, and the newly created request has `unlockAt = block.timestamp`. The settle guard `block.timestamp < request.unlockAt` evaluates to `false` immediately, so `completeWithdrawal` succeeds. The entire two-phase exit becomes a single atomic action, circumventing the intended protection against rapid market exits or front-running during pauses.

**Conditions required:** Deployment with `cooldown_ = 0`. The vault constructor passes the value through without validation:

```solidity
withdrawalQueue = new WithdrawalQueue(address(this), cooldown_);
```

and `WithdrawalQueue` also has no check:

```solidity
constructor(address vault_, uint64 cooldown_) {
    require(vault_ != address(0), "VAULT_ZERO");
    vault = vault_;
    cooldown = cooldown_;   // no minimum enforced
}
```

**Fix:** Add `require(cooldown_ > 0, "ZERO_COOLDOWN");` in the `StakingVault` constructor (or in `WithdrawalQueue`).

## [LOW] StakingVault — `setGuardian` accepts the zero address, silently removing the role

**File:** `src/core/StakingVault.sol`  
**Function:** `setGuardian()` (line 201)

**What an attacker can do:** If the owner mistakenly calls `setGuardian(address(0))`, the guardian role is permanently voided without any warning: `pause()` requires `msg.sender == owner || msg.sender == guardian`, and `address(0)` can never be a transaction sender. Only the owner retains the ability to pause, removing the intended secondary safety valve.

**Conditions required:** Owner calls `setGuardian(address(0))` (accidentally or under social-engineering pressure).

```solidity
function setGuardian(address newGuardian) external onlyOwner {
    emit GuardianUpdated(guardian, newGuardian);
    guardian = newGuardian;   // no zero-address check
}
```

**Fix:** Add `require(newGuardian != address(0), "GUARDIAN_ZERO");`.

## [LOW] Ownable2Step — `transferOwnership` accepts the zero address

**File:** `src/auth/Ownable2Step.sol`  
**Function:** `transferOwnership()` (line 30)

**What an attacker can do:** Calling `transferOwnership(address(0))` silently cancels any in-flight ownership handover by overwriting `pendingOwner` with the zero address. Because `acceptOwnership` requires `msg.sender == pendingOwner`, and the zero address can never sign a transaction, any previously nominated new owner is effectively disinherited with no on-chain indication that this was intentional. A compromised or pressured owner could use this to block a planned ownership transfer.

**Conditions required:** Owner calls `transferOwnership(address(0))`, whether accidentally or deliberately.

```solidity
function transferOwnership(address newOwner) external onlyOwner {
    pendingOwner = newOwner;    // zero address accepted
    emit OwnershipTransferStarted(owner, newOwner);
}
```

**Fix:** Add `require(newOwner != address(0), "OWNER_ZERO");`. A separate `cancelOwnershipTransfer()` function is the idiomatic way to express an intentional cancellation.

## [INFORMATIONAL] FixedPointMath — `mulDiv` uses native multiplication, which can overflow before the result fits

**File:** `src/libraries/FixedPointMath.sol`  
**Function:** `mulDiv()` (line 14)

**What can happen:** The expression `(x * y) / d` will revert on overflow if the intermediate product exceeds `type(uint256).max`, even when the mathematically correct result `x * y / d` would fit in a `uint256`. This affects share price calculations (`convertToShares`, `convertToAssets`) and reward index accumulation. With realistic ERC-20 token supplies and 18-decimal precision the overflow threshold is far beyond practical values, but this differs from the full 512-bit `mulDiv` used in production DeFi libraries.

**Conditions required:** Extremely large values of `assets`, `supply`, or `globalIndex` — not reachable with any standard token supply.

**Fix:** Replace with a full 512-bit multiply-then-divide (as in OpenZeppelin's `Math.mulDiv` or Uniswap v3's `FullMath.mulDiv`) if values approaching `2^128` are anticipated.
